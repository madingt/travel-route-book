# 分工：强模型规划，便宜模型干体力活

一份路书里，真正需要判断的只有几步：定骨架、选候选、留不留这家店、冲突了怎么改、反向审查。剩下的大量工作都是机械的：打开几十个页面，把门牌、营业时间、预约规则抄成固定格式，再按清单给笔记打标。机械的部分交给 Haiku 这类便宜模型，确定性的部分交给脚本，规划者只读一页摘要。

| 角色 | 谁来做 | 做什么 | 不做什么 |
|---|---|---|---|
| 规划者 | 主会话（强模型） | 第 0–2 步、选候选、读 `digest`、决定去留、改冲突、反向审查 | 不读原文，不逐个抄字段 |
| 采集员 `agents/page-collector.md` | Haiku × **1**（串行） | 按 `collect.jsonl` 打开网页，原样存进 `raw/` | 不判断，不登录 |
| 核对员 `agents/poi-checker.md` `ticket-checker.md` `xhs-grader.md` | Haiku × N（并行） | 读一张卡和它的原文，输出固定 JSON，每个字段附逐字引文 | 不联网，不决定去留 |
| `scripts/delegate.py` | 程序 | 生成任务卡、校验结果、记录每张卡的状态、合并进 `trip.json`、查冲突 | 不判断「哪家才是对的」 |
| 用户本人 | 人 | 登录、扫码、验证码、付款、下单预约 | — |

**采集只能串行，处理才能并行。** 浏览器只有一个，高德和小红书又依赖登录态，多个 agent 同时操作会互相踩。所以只派一个采集员按清单顺序跑，原文落盘之后，核对员才并行开工。

## 什么时候用
- 任务卡多（参考值：十几张以上）、想省时间，而且有能指定模型的 Agent/子 agent 工具时才派发。实测（仓库 `bench/RESULTS.md`）：10 张卡并行，时间约为一个模型全做的一半，但每个子 agent 有固定的启动开销，token 总量反而是 6–8 倍。卡少时规划者直接做，更快也更省。
- 没有 Agent 工具时，**照样走这套文件流程**：规划者自己按 `agents/*.md` 的说明逐张处理。校验、合并、冲突检查的好处一样拿得到。
- 境外行程（`"map": "google"`）不生成 POI 卡：用地点搜索工具拿到的本来就是结构化数据，直接填进 `trip.json`。预约卡和小红书卡照常使用。

## 流程
在工作目录下（`work/` 只是示例名）：

1. **出卡**：`python3 scripts/delegate.py init trip.json work/`
   - 大陆行程中每个需要核对的地点生成一张 POI 卡，并写入采集任务。已有 `amap_id` 和 `hours_week` 的跳过；占位条目（状态为「未定位」且没有门牌）也跳过。
   - **卡号按内容算，不按位置算**：卡号是「城市 + 店名 + 门牌线索」的哈希（预约卡是「场馆 + 日期」）。调整顺序、插入新地点，已核对的结果照样有效；换了店或改了门牌，就是一张新卡，旧结果不会被套到新地点上。同一个地点出现两天，只出一张卡。
   - 行程里删掉的地点，它的卡会「退役」（文件保留，不再派发）；地点加回来，原结果直接复用。所以**改了 `trip.json` 就重跑一次 `init`**，随时可以重跑。
   - `"booking": true` 的地点生成预约卡。用网页搜索找到**官方**页面后，执行 `delegate.py add-source work/ <卡号> <url>` 登记。
   - 小红书候选：`delegate.py add-xhs work/ "<店名>" --query "<搜索词>" [--query …] [--taste "只喝黑咖啡"]`。搜索词按 `references/xhs-screening.md` 来写：用中性词，不要把「避雷」当搜索词。改了口味限制或搜索词，之前的打标结果自动作废，需要重打。
2. **采集（串行）**
   - 有 `AMAP_KEY`：`delegate.py capture-amap trip.json work/` 由脚本取 POI 原文，不需要浏览器。
   - 其余任务：派**一个**采集员（见下文「怎么派发」），告诉它 `work/` 的位置。
   - 采集员遇到登录或验证会记进 `work/raw/_blocked.txt` 并跳过。这时请用户**自己**在浏览器里登录，再派一次采集员（它会跳过已经存好的文件）。
3. **核对（并行）**：`delegate.py pending work/` 会按 worker 分组列出该派的卡。每张卡派一个核对员，一批 5–8 个。派之前先 `delegate.py claim work/ <卡号…>`，这些卡会标成 `running`，不会被重复派发；核对员 20 分钟没交结果，卡自动放回待派，并记一次失败。
4. **校验**：`delegate.py check work/`。每张卡落在五种状态之一（见下文「任务状态」）。`failed` 的卡，`pending` 会把失败原因列出来，把原因附在提示里重派一次；同一张卡失败两次，转成 `needs_review`，由规划者亲自处理。
5. **读摘要**：`delegate.py digest work/` 一张卡一行。规划者**只读这个**，不要去读 `raw/` 或 `out/`。只有某一行有疑点时，才打开那一张卡的 `out` 文件。
6. **合并**：先 `delegate.py merge trip.json work/` 预览，再加 `--write` 保存。只合并 `succeeded` 的卡。门牌、营业时间、坐标、地点状态、抢票清单、待核实和信息来源会自动回填；每个回填过的地点带一个 `provenance`（来自哪张卡、可信度）。小红书结果**不会**自动写入，因为留不留是规划者的决定。
   - **重复合并是安全的**：没有新结果时什么都不写，`changelog` 也不会多一行。
   - 每个被改写前的版本都留在 `work/backups/`，最近一个另存为 `trip.json.bak`。
   - 合并时还会查两件事并写进待核实：两个不同名字的地点核到了同一个地图点；同一场馆不同日期核到的预约规则不一致。
   - 抢票清单里手写的条目不会被覆盖。想让脚本接管某条手写条目，给它加上 `"venue": "<场馆全名>"`。
7. **查冲突**：`delegate.py conflicts trip.json` 会对照每天的星期，检查当天是否休息、到店时间是否在营业时段内、离打烊是否太近、是否碰上闭馆日、是否晚于最晚入场；还会查 `iso_date` 和写的星期对不上、日期顺序错、放号时间已过、预约规则和地图营业时间互相矛盾。境外行程在 `trip.json` 顶层写 `"timezone": "Asia/Tokyo"`，「今天」和放号时间才按当地算。出现 ERROR 时，由规划者换店或换时间。新换的店加进 `trip.json` 后重跑 `init`，只会为新地点出卡。
8. 然后回到 SKILL.md 第 6 步（反向审查）和第 7 步（输出）。

## 任务状态
`delegate.py status work/` 随时列出每张卡的状态。状态存在 `work/state.json`，每次变化记进 `work/events.jsonl`。中途断了（会话结束、电脑关机），重新打开后跑 `status` 和 `pending`，从断的地方接着做，已完成的卡不会重派。`state.json` 丢了也没关系，会根据文件重建。

| 状态 | 含义 | 下一步 |
|---|---|---|
| `pending` | 还没有可用结果（或者旧结果已作废） | 没原文先采集，有原文就派核对员 |
| `running` | 已 `claim`，核对员在做 | 等；超时自动放回 |
| `succeeded` | 通过全部校验 | 可以合并 |
| `failed` | 结果不合格（原因带代码，如 `QUOTE_NOT_FOUND`） | 把原因附上，重派一次 |
| `needs_review` | 需要人或规划者处理，**不会再派给 worker** | 见下 |

`needs_review` 的三种情况：
- `HUMAN_ACTION_REQUIRED`：采集时碰到登录、扫码、验证码。**请用户自己**在浏览器里完成，然后 `delegate.py unblock work/ <卡号>`，再派一次采集员。任何 agent 都不替用户输入账号、密码、验证码，也不替用户下单、付款、提交预约。
- `RETRIES_EXHAUSTED`：核对员失败两次。规划者亲自按 `agents/*.md` 的格式写这张卡的结果。
- `VALUE_NOT_IN_QUOTE`：引文是真的，但引文里看不出填的那个值（比如填了提前 30 天，引的却是闭馆日那句）。打开这张卡的 `out` 文件对照原文：值错了就改，确认没错就 `delegate.py approve work/ <卡号> --by <谁看的> --note "<依据>"`。批准只对这一份结果有效，结果一改就要重新看。

## 校验能证明什么，不能证明什么
脚本做的是确定性检查，不经过模型：
- 结果的格式和类型对不对；是不是给**当前这张卡**写的（`fingerprint` 对不上就拒收）；
- 引用的文件存在，引文（8–200 字）逐字出现在**那个文件**里；
- 店名、POI 编号、电话、坐标、来源网址，在原文里找得到原样的字符；
- 时间、提前天数、闭馆日、票价、门牌，在各自的引文里看得见。

脚本**证明不了**的事，仍然是模型的判断，规划者要心里有数：
- 逐字引文只说明「保存下来的网页里有这句话」，不说明网页内容是对的、是最新的、是官方的，也不说明这句话说的就是这家店；
- 多个候选里选的是不是对的那一家（分店、同名店）；
- 小红书笔记的立场、是不是营销号；`confidence` 高低；
- `required`、`real_name`、`same_day` 这类是/否字段，以及预约渠道的名字。

所以：`succeeded` 的意思是「没发现问题」，不是「已证实」。预约规则写进抢票清单后，仍然要提醒用户出发前自己到官方渠道确认一次。

## 怎么派发
- **Claude Code 里已经注册过**（`agents/*.md` 已复制到 `~/.claude/agents/` 或项目的 `.claude/agents/`）：按名字调用，例如 `poi-checker`。模型和工具限制在文件的 frontmatter 里已经写好。
- **没注册，或者不在 Claude Code 里**：读对应的 `agents/<名字>.md`，把正文（frontmatter 以下）作为提示，在 Agent 工具里把模型指定为 `haiku`，再在末尾附上：
  ```
  任务卡：work/tasks/<卡号>.json
  work 目录：work/
  （重派时）上次校验没通过的原因：<pending 列出的原因，连同代码>
  ```
- 核对员回复只有一行，结果写在文件里。**不要**让它们把 JSON 贴回对话，否则内容又会流经规划者的上下文。

## 规划者怎么用摘要做决定
- **地点**：`not_found` 往往说明店已经关了，换一家；`ambiguous` 要选定具体是哪一家；有 `closed_notice` 时，先看清再决定。
- **预约**：`待核实` 的字段写进抢票清单的同时，也要在回复里提醒用户自己确认；规则年份太旧时，不要直接照用。
- **小红书**（经验阈值，最后仍由你判断）：
  - 出现「预制菜、卫生、冷菜回锅」这类致命差评 → 划掉；
  - 独立好评 ≥ 2 篇，且没有致命差评 → 可以作为核心正餐；
  - 独立好评只有 1 篇 → 放进随缘备选；
  - 营销笔记占多数，又没有独立好评 → 当作噪音。
  - 留下的店，理由要引用 `real_signals` 里的原句。只有这时才需要打开那张卡的 `out` 文件。

## 省在哪里
- 网页原文只经过采集员和核对员（便宜模型），规划者只看 `digest`。
- 校验、合并、日期推算、营业时间对照都是脚本完成的，不消耗模型。
- 迭代时只为新增或改动的地点出卡，`trip.json` 里已经核过的不再重复跑。
- 实测对比（一个强模型全做 / 一个便宜模型全做 / 每张卡一个便宜模型）见仓库的 `bench/RESULTS.md`。
