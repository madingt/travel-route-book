# 旅游攻略路书（Travel Route Book）

方法来源：少数派 胡九思《别再把攻略全甩给 AI》（sspai.com/post/114945），并吸收了多次真实行程规划中踩过的坑。
核心立场：**不要一句话生成流水账**。人定方向与取舍，Agent 干体力活（查资料、核地址、算距离、理冲突、排版、把地点落进手机地图）。路书是**活文档**：同一份 `trip.json`、同一个链接，一轮轮迭代。

## 四条原则（每一步都过一遍）
1. **从噪音里识别信号**：只有能直接支撑决定（住哪、几点抢票、这家去不去）的信息才进行程。
2. **一手信息优于二手转述**：时间、门票、预约、放号、闭馆、营业时间，回到官网/官方小程序/公众号/地图 App 核对。核对不到就标「待核实」，绝不凭记忆写。
3. **信任具体的人，胜过信任算法**：评论区里带错字、口语化的真实碎碎念 > 精修爆款笔记。
4. **输入质量决定输出质量**：先收齐底稿、官方原文、评论细节、地图数据，再融合。

## 第 0 步：收集信息（一次问完）
出发地与**到达方式（机场/车站名）**、到达与返程的具体时间、日期与天数、同行人与作息、主题、必去/必避、住宿偏好（是否分段住）、体力节奏、口味偏好、预算。
- 已在上下文或记忆里的不再问；用户不在场时取最合理假设，写进 `assumptions`。
- **核心事件（演出、开放日、会议）的确切时间地点要尽早拿到**：它决定整天骨架和住在哪。拿不到就做「上午版/下午版」两套，拿到后立刻收敛。
- 作息约束（「前一天还在上班」「上午落地」）落到第一天的强度上：到达日只排步行和吃喝，不排要预约或赶点的项目。

## 第 1 步：定目标与骨架
- 出行类型：打卡式 / 度假式 / 主题式。主题决定去哪、舍弃什么。
- 先出**骨架**：每天住哪、核心动线、交通方式与时长（时长用地图路线规划查，不要估）。
- 住宿可以分段：离核心事件近的那晚住过去，其余住交通枢纽。分段住要同步处理**行李**：到达日没酒店放包 → 查寄存点；换住处那天 → 先放行李再出门。
- 用工作日/周末错峰：热门湖景/寺庙放工作日清晨，周末去城市外围。

## 第 2 步：挑景点（做减法）
- 候选来源交叉比对：Agent 列候选 + 真实游客笔记（方法见 `references/xhs-screening.md`）。
- 舍弃偏离主线、绕路、高峰期体验打折的点；每个舍弃写一句理由进 `appendix.dropped`。
- 主题偏好贯彻到底（喜欢建筑 → 列建筑师作品；喜欢徒步 → 给路线、距离、爬升、退出点）。

## 第 3 步：一手信息核对 + 抢票日历
- 每个需要预约的点核对：渠道（小程序/公众号名）、提前几天、几点放号、是否接受当天预约、闭馆日、最晚入场、开放对象。规则发布年份要看清，旧规则标「待核实」。
- 写进 `tickets`：哪天几点、在哪个平台、约什么。日期改了要整体重算放票日。

## 第 4 步：地图核实
- **中国大陆用高德，大陆以外用谷歌**（谷歌在大陆网络下通常加载不出来）。
- 每个地点核对门牌、营业时间、坐标，回填 `trip.json`；**营业时间逐条对照行程时段**，冲突就换店或换时间。搜不到的店当成信号（可能已关）。
- 详细做法：`references/amap-web.md`（有 `AMAP_KEY` 用 `scripts/amap_lookup.py`，没有就用网页版）/ `references/google-maps.md`。

## 第 5 步：餐饮/咖啡匹配
- 每天 1–2 家核心正餐贴合动线，其余放 `backups`。
- 口味过滤贯彻到底（如只喝黑咖啡 → 排除以特调/奶咖出名、手冲被吐槽的店，写明原因）。
- 每家写：门牌、最近地铁口、营业时间、为什么留下（引用真实评论）。

## 第 6 步：反向审查（必做）
以专业导游视角质询：体力透支、同日跨区折返、闭馆日（多数博物馆周一闭馆）、营业时间冲突、预约放号日、行李、到达日强度、返程缓冲（起飞前 3 小时从市区出发）、雨天方案。问题与改法写进 `appendix.review`。

## 第 7 步：输出
1. `scripts/build_routebook.py` 生成 HTML 路书 → `scripts/test_routebook.cjs` 必须 PASS → 发布（有 Artifact 工具就发布到同一 URL）并附离线文件。详见 `references/routebook-html.md`。
2. 大陆行程且条件满足时，把地点落进手机高德的分天路线（`references/amap-iphone-mirroring.md`）；不满足就给 `scripts/map_links.py` 的每日地图链接。
3. 用户要表格时：`scripts/trip_to_xlsx.py`。

## 第 8 步：临近复核
- 出发前约一周的预报才可信。有定时/提醒工具（如 send_later）就在**出发前 2 天上午**安排一次复核；没有就在回复里提醒用户那天回来找你。
- 复核内容：中央气象台 nmc.cn + 另一来源交叉；按天气逐日调整户外段；把调整写进 `notice` 和 `changelog`，重跑脚本、重新发布；同步更新手机高德路线；用最醒目的方式告诉用户需要立刻动手的事。
- 定时提示词要自带全部上下文：路书链接、`trip.json` 位置（容器可能被回收，回收后先取回已发布的路书）、日期、住宿、核心事件、调整规则。

## 每轮回复
一句话说改了什么 + 列关键调整 + 还需要用户做的事。不复述整份行程。

## 不要做
- 凭记忆写门票、开放时间、放号规则、营业时间。
- 把营销笔记的店当推荐；把一篇笔记或热度榜当结论。
- 只给「区域」不给门牌；给了店却没核对营业时间和行程时段是否冲突。
- 在大陆用谷歌地图；手改生成的 HTML 而不改 `trip.json`；测试没过就发布。
- 替用户登录、输入验证码、勾选协议、抢票或下单。
- 未经同意打开用户相册、把路线设为公开、删除用户已有的收藏。
- 从早排到晚、到达日排重活、同日跨区来回折返。
