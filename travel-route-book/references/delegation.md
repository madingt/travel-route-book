# 分工：强模型规划，便宜模型干体力活

一份路书里，真正需要判断的只有几步：定骨架、选候选、留不留这家店、冲突了怎么改、反向审查。剩下的大量工作都是机械的：打开几十个页面，把门牌、营业时间、预约规则抄成固定格式，再按清单给笔记打标。机械的部分交给 Haiku 这类便宜模型，确定性的部分交给脚本，规划者只读一页摘要。

| 角色 | 谁来做 | 做什么 | 不做什么 |
|---|---|---|---|
| 规划者 | 主会话（强模型） | 第 0–2 步、选候选、读 `digest`、决定去留、改冲突、反向审查 | 不读原文，不逐个抄字段 |
| 采集员 `agents/page-collector.md` | Haiku × **1**（串行） | 按 `collect.jsonl` 打开网页，原样存进 `raw/` | 不判断，不登录 |
| 核对员 `agents/poi-checker.md` `ticket-checker.md` `xhs-grader.md` | Haiku × N（并行） | 读一张卡和它的原文，输出固定 JSON，每个字段附逐字引文 | 不联网，不决定去留 |
| `scripts/delegate.py` | 程序 | 生成任务卡、逐字校验引文、合并进 `trip.json`、查营业时间冲突 | — |

**采集只能串行，处理才能并行。** 浏览器只有一个，高德和小红书又依赖登录态，多个 agent 同时操作会互相踩。所以只派一个采集员按清单顺序跑，原文落盘之后，核对员才并行开工。

## 什么时候用
- 任务卡 ≥ 6 张，而且有能指定模型的 Agent/子 agent 工具时才派发。卡太少时，派发本身的开销比省下的还多，规划者直接做。
- 没有 Agent 工具时，**照样走这套文件流程**：规划者自己按 `agents/*.md` 的说明逐张处理。校验、合并、冲突检查的好处一样拿得到。
- 境外行程（`"map": "google"`）不生成 POI 卡：用地点搜索工具拿到的本来就是结构化数据，直接填进 `trip.json`。预约卡和小红书卡照常使用。

## 流程
在工作目录下（`work/` 只是示例名）：

1. **出卡**：`python3 scripts/delegate.py init trip.json work/`
   - 大陆行程中每个需要核对的地点生成一张 POI 卡，并写入采集任务。已有 `amap_id` 和 `hours_week` 的跳过；占位条目（状态为「未定位」且没有门牌）也跳过。
   - `"booking": true` 的地点生成预约卡。用网页搜索找到**官方**页面后，执行 `delegate.py add-source work/ <卡号> <url>` 登记。
   - 小红书候选：`delegate.py add-xhs work/ "<店名>" --query "<搜索词>" [--query …] [--taste "只喝黑咖啡"]`。搜索词按 `references/xhs-screening.md` 来写，记得加反查词（避雷、预制菜）。
2. **采集（串行）**
   - 有 `AMAP_KEY`：`delegate.py capture-amap trip.json work/` 由脚本取 POI 原文，不需要浏览器。
   - 其余任务：派**一个**采集员（见下文「怎么派发」），告诉它 `work/` 的位置。
   - 采集员遇到登录或验证会记进 `work/raw/_blocked.txt` 并跳过。这时请用户**自己**在浏览器里登录，再派一次采集员（它会跳过已经存好的文件）。
3. **核对（并行）**：`delegate.py pending work/` 会按 worker 分组列出该派的卡。每张卡派一个核对员，一批 5–8 个。
4. **校验**：`delegate.py check work/` 会检查格式、取值，以及**每条引文是否逐字出现在原文里**。不合格的卡，`pending` 会把失败原因列出来。把原因附在提示里重派一次；同一张卡失败两次，`pending` 会归到「planner: do it yourself」，由规划者亲自处理。
5. **读摘要**：`delegate.py digest work/` 一张卡一行。规划者**只读这个**，不要去读 `raw/` 或 `out/`。只有某一行有疑点时，才打开那一张卡的 `out` 文件。
6. **合并**：先 `delegate.py merge trip.json work/` 预览，再加 `--write` 保存（会留 `.bak` 备份）。门牌、营业时间、坐标、地点状态、抢票清单、待核实和信息来源会自动回填。小红书结果**不会**自动写入，因为留不留是规划者的决定。
7. **查冲突**：`delegate.py conflicts trip.json` 会对照每天的星期，检查当天是否休息、到店时间是否在营业时段内、离打烊是否太近、是否碰上闭馆日、是否晚于最晚入场。出现 ERROR 时，由规划者换店或换时间。新换的店加进 `trip.json` 后重跑 `init`，只会为新地点出卡。
8. 然后回到 SKILL.md 第 6 步（反向审查）和第 7 步（输出）。

## 怎么派发
- **Claude Code 里已经注册过**（`agents/*.md` 已复制到 `~/.claude/agents/` 或项目的 `.claude/agents/`）：按名字调用，例如 `poi-checker`。模型和工具限制在文件的 frontmatter 里已经写好。
- **没注册，或者不在 Claude Code 里**：读对应的 `agents/<名字>.md`，把正文（frontmatter 以下）作为提示，在 Agent 工具里把模型指定为 `haiku`，再在末尾附上：
  ```
  任务卡：work/tasks/<卡号>.json
  work 目录：work/
  （重派时）上次校验没通过的原因：<pending 列出的原因>
  ```
- 核对员回复只有一行，结果写在文件里。**不要**让它们把 JSON 贴回对话，否则内容又会流经规划者的上下文。

## 规划者怎么用摘要做决定
- **地点**：`not_found` 往往说明店已经关了，换一家；`ambiguous` 要选定具体是哪一家；有 `closed_notice` 时，先看清再决定。
- **预约**：`待核实` 的字段写进抢票清单的同时，也要在回复里提醒用户自己确认；规则年份太旧时，不要直接照用。
- **小红书**（经验阈值，最后仍由你判断）：
  - 出现「预制菜、卫生、冷菜回锅」这类致命差评 → 划掉；
  - 独立好评 ≥ 2 篇，且没有致命差评 → 可以作为核心正餐；
  - 独立好评只有 1 篇 → 放进随缘备选；
  - 营销笔记占多数，又没有独立好评 → 当作噪音。
  - 留下的店，理由要引用 `real_signals` 里的原句。只有这时才需要打开那张卡的 `out` 文件。

## 省在哪里
- 网页原文只经过采集员和核对员（便宜模型），规划者只看 `digest`。
- 校验、合并、日期推算、营业时间对照都是脚本完成的，不消耗模型。
- 迭代时只为新增或改动的地点出卡，`trip.json` 里已经核过的不再重复跑。
